## Assessment Methodology

For each of the 7 weakness categories listed in the Day 4 roadmap brief,
the assessment captures:
1. **State** — what the current code actually does
2. **Risk** — concrete impact if exploited
3. **Disposition** — fixed in this PR / deferred to specific roadmap day / not applicable

Tools used: `mobsfscan` (Day 3), `semgrep` (Day 3), targeted code review
(`grep`, `Read`).

## Assessment Results — 7 Weakness Categories

### 1. Weak SSL pinning

**State.**
- No `ssl_pinning_plugin` / `http_certificate_pinning` / `dio_ssl_pinning` in [pubspec.yaml](pubspec.yaml).
- No `CertificatePinner` / `HostnameVerifier` / `TrustManager` code anywhere.
- [api_error_handler.dart](lib/core/networking/api_error_handler.dart#L24) handles `DioExceptionType.badCertificate` only as a generic error — no pinning enforcement.
- Day 3 partial mitigation in place: [network_security_config.xml](android/app/src/main/res/xml/network_security_config.xml) — HTTPS-only + system CAs only in release; user-installed CAs blocked.

**Risk.** With only system-CA trust (no SPKI pinning), any compromised or rogue CA in Android's system trust store can issue a valid cert for `vcare.integration25.com` and intercept patient PHI in transit.

**Disposition.** ⏸ **Deferred to Day 8** — SSL pinning needs:
- Production cert SPKI hashes from the backend team
- A rotation strategy (pin backup hashes for cert rotation)
- A fail-open/fail-closed decision for old app versions

---

### 2. Secrets in shared_preferences

**State.**
- [shared_pref_helper.dart](lib/core/helpers/shared_pref_helper.dart) exposes both `SharedPreferences` (plain) and `FlutterSecureStorage` (Keystore/Keychain).
- Tokens are stored via `setSecuredString` ([login_cubit.dart:22](lib/features/login/presentation/cubit/login_cubit.dart#L22), [register_cubit.dart:35](lib/features/register/presentation/cubit/register_cubit.dart#L35)) → backed by Android Keystore. ✅ Storage choice is correct.
- 🚨 **However**, `debugPrint` previously logged the **value** of the secret being stored at [shared_pref_helper.dart:97](lib/core/helpers/shared_pref_helper.dart#L97):
  ```dart
  debugPrint("FlutterSecureStorage : setSecuredString with key : $key and value : $value");
  ```
  Plus `setData` logged the plain value at line 26.

**Risk.** Any secured string written through the helper (auth tokens, OTPs, future PHI) was emitted to `logcat` in **every build, including release**. `flutter`'s `debugPrint` is not gated by build mode by default — it ships in release. A malicious app with `READ_LOGS` (granted on rooted devices, used by Frida hooks during pentest) would scrape every token written.

**Disposition.** ✅ **FIXED in this PR.** Removed `$value` from both `debugPrint` calls (keys only). Verified with `flutter analyze` clean + `flutter build apk --debug` 14.9s.

### 6. Biometric without fallback control

**State.**
- [security_settings_screen.dart](lib/features/home/presentation/screens/security_settings_screen.dart) shows toggles for **"Face ID / Biometrics"** and **"PIN Lock"** that persist user preferences.
- No `local_auth` package in pubspec.
- No biometric prompt enforcement anywhere — toggles set flags that nothing reads.

**Risk.** The user-visible **claim** of biometric protection is misleading: the app appears to offer Face ID gating but, because no biometric API is invoked, the gate is unenforced. A user trusting that toggle will leave the app effectively unlocked. Reputational and compliance risk (HIPAA, GDPR).

**Disposition.** ⏸ **Deferred to Day 29** (Biometric authentication deep dive). Day 29 needs to:
- Wire `local_auth` to those toggles
- Decide fallback behavior (PIN? device credential? deny entry?)
- Handle the BiometricNotEnrolled / BiometricUnavailable / UserCancel branches
- Make the "Face ID" toggle actually do something OR remove it

### 7. JWT authentication without refresh token rotation

**State.**
- [dio_factory.dart](lib/core/networking/dio_factory.dart) attaches `Authorization: Bearer <token>` from secure storage on every request via `_TokenInterceptor`.
- No `onError` handler for `401 Unauthorized` in the Dio interceptor stack.
- No refresh-token endpoint call, no token rotation, no retry logic.
- 🚨 **Additional finding:** `PrettyDioLogger` was configured with `requestHeader: true` and `requestBody: true` in **all builds** ([dio_factory.dart pre-Day-4](lib/core/networking/dio_factory.dart)). The Bearer token was emitted to `logcat` for every API request in release.

**Risk.**
- Without refresh + rotation, a stolen token is valid until manual revocation. Combined with the secret-value `debugPrint` leak (finding 2), token compromise was trivial.
- Long-lived tokens cannot be invalidated server-side without an explicit logout endpoint flow.

**Disposition (token rotation).** ⏸ **Deferred to Day 12** (JWT vs sessions) — needs:
- Backend `/auth/refresh` endpoint with refresh-token rotation
- Client-side refresh queue (avoid thundering herd when token expires mid-burst)
- Sliding session / absolute expiry policy

**Disposition (logger token leak).** ✅ **FIXED in this PR.** [dio_factory.dart](lib/core/networking/dio_factory.dart):
- Logger now wrapped in `if (kDebugMode)` — not added to interceptors in release at all
- `requestHeader: false` even in debug, so `Authorization` never lands in any log
- Inline comment points to Day 38 (PII leakage in crash reporting and logging) for an opt-in remote logger

## 20-Question Entrance Test — Mobile Security Basics

> Self-assessment to evaluate baseline. Mark each answer **before** scrolling
> to the answer key. Score: 18-20 = Architecture-ready, 14-17 = Senior
> Security, 10-13 = Senior Dev, < 10 = Foundation needed.

1. On Android, where is the safest place to store an OAuth refresh token?
2. What is the practical difference between `flutter_secure_storage` on Android and on iOS, at the platform-API level?
3. What does `cleartextTrafficPermitted="false"` do in a network security config, and when does it **not** apply?
4. Why is pinning the certificate of a leaf certificate considered worse than pinning the SPKI hash?
5. What is the difference between a public-key pin and a certificate-chain pin? Which one survives cert rotation more gracefully?
6. What does `android:allowBackup="false"` defend against, and what does it NOT defend against?
7. Why is a Firebase `apiKey` value safe to ship in client code, while a Google Cloud service account JSON is not?
8. Describe the **StrandHogg 2.0** task-hijacking attack class in one sentence. What is the standard manifest-level mitigation?
9. What does `FLAG_SECURE` prevent? Name one legitimate user workflow it might block.
10. On iOS, what is the equivalent of `FLAG_SECURE` and at what API does it live?
11. What is the difference between **JWT signature validation** and **JWT claim validation**? Which one tells you the token is genuine, and which tells you it is still valid?
12. Name two attacks that **refresh-token rotation** mitigates that long-lived access tokens do not.
13. What is a **WebView JavaScript bridge**, and why is `@JavascriptInterface` historically dangerous on Android < 4.2?
14. Why does Android consider an Activity exported by default if it has any `<intent-filter>` declared? What attribute makes the export explicit?
15. What is the difference between an **Android deep link** (`scheme://path`) and an **App Link** (`https://` + `autoVerify`)? Which one prevents intent hijacking by another app?
16. Name two Frida / Objection capabilities that are blocked by an unrooted device.
17. What does the **Play Integrity API** verdict tell you about a device, app, and account? What does it NOT tell you?
18. What is **MASVS-RESILIENCE**, and which two profiles of the OWASP MAS standard explicitly require it?
19. Why is `dart:ffi` a larger attack surface than a typical Dart-only package? Name two concrete risks.
20. In Flutter AOT release builds, where in the APK does the Dart code end up, and what tool (covered in Day 2) extracts class/method symbols from it?

<details>
<summary>Answers — click to expand</summary>

1. **Android Keystore via `flutter_secure_storage` (which uses `EncryptedSharedPreferences` + Keystore-backed key).** Plain `SharedPreferences` is a flat XML file readable on rooted devices.
2. **iOS:** Keychain Services API (hardware-backed via Secure Enclave on A7+); accessibility class controls when readable. **Android:** EncryptedSharedPreferences with a master key in AndroidKeystore (hardware-backed via StrongBox on supported devices).
3. Blocks plain-HTTP traffic from the app's network stack. **Does not** apply to traffic through `dart:io.HttpClient` if `badCertificateCallback` returns `true`, NDK libraries that use their own networking stack, or WebViews (which have their own setting).
4. Leaf certs rotate often; pinning to a leaf means an outage every rotation. SPKI hash pins the public key, which usually survives cert renewal (same CSR keypair). Cert pin is also bypassable if an attacker controls the cert generation pipeline; SPKI pin requires private-key compromise.
5. Public-key pin = SPKI hash; survives cert rotation as long as the keypair is reused. Cert-chain pin = pin to a specific intermediate or root; allows leaf rotation by the CA. **SPKI pin is more rotation-friendly** in practice.
6. Defends against: `adb backup`, Google Auto Backup uploading app data to user's Google Drive. Does **not** defend against: a rooted device pulling `/data/data/<pkg>/`, full disk encryption bypass, or screenshots/Recents.
7. Firebase `apiKey` identifies the Firebase **project**, not a user — it has no authority on its own; security is enforced by **Firebase Security Rules + App Check**. A service-account JSON contains the signing key for asserting any identity in that project.
8. StrandHogg 2.0: a malicious app launches itself with a `taskAffinity` matching the victim's task and a malicious launchMode, so it gets pushed onto the victim's task stack and shown when the user resumes the victim app. Mitigation: `android:taskAffinity=""` on the launcher activity + targetSdk ≥ 29 (Android 10 fixed the underlying multi-task issue).
9. Sets `FLAG_SECURE` on the window → screen contents excluded from screenshots, screen recordings, the Recents thumbnail, and external display mirroring (e.g. AirPlay/Cast). **Blocks** legitimate screenshot use cases (sharing X-rays, troubleshooting with support).
10. iOS does not have a direct equivalent. Closest patterns: cover the window with a blur view when the app enters `applicationWillResignActive`, and set `UIScreen.isCaptured` observers for screen recording. There is **no API** to block screenshots on iOS.
11. **Signature validation** verifies the token was issued by an entity holding the signing key (HMAC secret / RSA private key) → "this token is genuine." **Claim validation** checks `exp`, `nbf`, `aud`, `iss` (and revocation lists if available) → "this token is still valid for this request."
12. (a) **Token theft window shrinks** — short-lived access tokens limit damage from log/transit leaks. (b) **Rotation detects replay** — when a rotated refresh token is replayed, the server can invalidate the family (RFC 6749 §10.4) and forcibly log the user out across all sessions.
13. A bridge is a Java/Kotlin object exposed to the WebView's JS context via `addJavascriptInterface`. Before Android 4.2 (API 17), any reachable method, including `getClass()`, was callable → reflection → arbitrary code execution. `@JavascriptInterface` annotation (added API 17) is required for a method to be visible to JS.
14. Historical default: exporting was implicit if an `<intent-filter>` was declared, so other apps could `Intent` your activity. Modern Android (API 31+) **requires explicit** `android:exported="true|false"` when an intent-filter is present; AGP will fail the build otherwise.
15. Deep link = generic URI scheme handled by any app that registers the scheme (`docdoc://`); the system shows a chooser if multiple apps claim it. **App Link** = `https://` URL with `android:autoVerify="true"` + a `/.well-known/assetlinks.json` hosted on the domain, which the OS verifies. Only the verified app gets the intent — no hijacking by malicious apps registering the same scheme.
16. (a) Spawning the target app under a Frida server (needs root to push frida-server to `/data/local/tmp/` and start it). (b) Reading/writing `/data/data/<pkg>` (private app sandbox). On unrooted devices, Frida can still attach to debuggable builds, or run via gadget injection in repackaged APKs.
17. Play Integrity verdict reports: **device integrity** (`MEETS_DEVICE_INTEGRITY` / `MEETS_BASIC_INTEGRITY` / `MEETS_STRONG_INTEGRITY`), **app integrity** (untampered signature), **account details** (licensed to current user). It does **not** report: whether root tools are installed but inactive, whether the user has admin/dev tools, whether the app is being instrumented in memory, or guarantee any specific timing of detection.
18. MASVS-RESILIENCE is the OWASP MAS control category for anti-reverse-engineering and runtime application self-protection. Required in **L2 (defense-in-depth)** and **R (resilience)** profiles, not in L1 (standard baseline).
19. (a) The boundary is now a **C ABI** — memory safety guarantees of Dart don't apply; a buffer overflow in the native lib is a Dart-side RCE. (b) Native code can be **dlopen**ed at runtime from arbitrary paths — supply-chain integrity (Day 47 covers this) becomes a runtime concern, not just a build concern.
20. Dart AOT code lives in `lib/<abi>/libapp.so` inside the APK (e.g. `lib/arm64-v8a/libapp.so`). **Blutter** (Day 2) parses the AOT snapshot in `libapp.so`, recovers Dart class/method symbols, and emits a Ghidra script for annotation.
